# StoryLM 预训练工作全记录

> 从零实现 → 数据与分词器 → 预训练 → 超参扫描 → 稳定性边界 → 架构消融 → 生成评估
> 每个阶段按"遇到的问题 → 解决思路 → 做了什么 → 结果"组织。
> 原始数据：`exp/experiment_log.md`（EXP-001~010）、`README.md`、`logs/*.csv`、`figures/`。

---

## 0. 项目定位

目标不是"调通一个模型"，而是**验证对 Transformer 底层的真实掌握**：不使用
`nn.Linear` / `nn.MultiheadAttention` / `nn.LayerNorm` 等任何高层模块，全部权重以
`nn.Parameter` + 手写前向实现（attention / RoPE / RMSNorm / SwiGLU / 线性层 /
embedding），并手写 BPE 分词器、AdamW、cosine 调度、梯度裁剪、checkpoint。
在此之上，把"跑通"升级为"实验"：系统的超参扫描、发散边界分析、四组架构消融。

**硬件**：单张 RTX 4090（24GB），全程开启 `torch.compile`。

---

## 1. 最终模型与训练配置（先给结论）

| 项 | 值 |
| --- | --- |
| 架构 | Decoder-only Transformer（LLaMA 风格） |
| 参数量 | 22.7M（非嵌入 12.5M；untied embedding / lm_head） |
| 层 / d_model / 头 | 4 / 512 / 16 |
| FFN | SwiGLU，d_ff=1344（≈8/3·d_model，三矩阵门控） |
| 位置编码 | RoPE（θ=10000） |
| 归一化 | RMSNorm，Pre-Norm |
| 词表 / 上下文 | 10000（BPE）/ 256 |
| 初始化 | 截断正态（std=0.02） |
| 优化 | AdamW（β 0.9/0.999，ε 1e-8）+ wd 0.1 + 梯度裁剪 1.0 + warmup 10M tokens + cosine→0.1× |
| 训练量 | 3.28 亿 tokens（19531 步 @ bs64） |
| **最佳验证损失** | **1.2994**（per-token 交叉熵；目标门槛 ≤1.45，大幅超出） |
| 训练耗时 | ~24 分钟（≈23 万 tokens/s） |

## 2. 问题一：手写实现怎么证明没有 bug？

**问题**：全部手写意味着 attention 掩码、RoPE 旋转方向、RMSNorm 公式、梯度流
任何一处写错，模型都可能"能训但不收敛"或"收敛但次优"，且错误隐蔽难查。

**解决思路**：多层验证，先单元后全局，先过拟合后收敛。

**做了什么**：
1. **单元测试套件**（`tests/`）：分词器（编码/解码往返、训练速度）、模型算子
   （各组件数值行为）、优化器（AdamW 更新公式）、序列化（checkpoint 存取）、
   数据管道——逐组件锁定正确性。
2. **单 batch 过拟合自检**（`overfit_test` 子命令）：实现正确的模型在单个
   batch 上应快速把 loss 压到 ~0；这是排查前向/反向错误的最快手段。
3. **确定性验证评估**：评估固定种子与数据顺序，保证实验间可比。

**结果**：baseline 一次训练收敛到 1.2994，远优于 1.45 门槛；实现全程未出现
"能跑但错"的隐蔽 bug。

---

## 3. 问题二：2.23GB 语料，分词器和数据怎么不爆内存？

**问题**：完整 TinyStories 训练集约 2.23GB，BPE 训练需要反复扫描全语料统计
pair 频次，一次性载入内存不可行。

**解决思路**：分块处理 + 先冒烟后全量 + mmap 按需读取。

**做了什么**（EXP-001 / EXP-002）：
1. 先在 22MB 验证集上冒烟测试 BPE 实现（21.9s 训出 10K 词表），验证
   时间与内存行为可接受；
2. 分块（4 chunks）训练完整语料的分词器：**14.2 分钟**训完，10,000 词表
   （256 字节 token + 1 特殊 token `<|endoftext|>` + 9,743 个学习到的合并）；
   冒烟阶段发现分块对速度无益（21.9s vs 22.1s），其真正价值是内存管理；
3. 语料编码为 `uint16` 的 `.npy`，训练时 **mmap 按需读取**，避免整个数据集
   常驻内存；
4. 产出 `data/vocab.json` + `data/merges.txt`，编码后语料供训练直接消费。

## 4. 问题三：学习率没有先验，怎么选？

**问题**：手写 AdamW + 自定义架构，网上经验值不可信；lr 太小欠拟合、太大
不稳定，需要自己扫。

**解决思路**：固定其余全部超参（bs=64，3.28 亿 tokens），7 档对数间隔扫描，
覆盖保守到激进。

**做了什么**（EXP-004）：

| lr | 1e-4 | 3e-4 | 1e-3 | **3e-3** | 5e-3 | 1e-2 | 3e-2 |
| -- | ---- | ---- | ---- | ------ | ---- | ---- | ---- |
| 最佳 val | 1.4724 | 1.3470 | 1.3013 | **1.2960** | 1.3175 | 1.4073 | 1.7426 |

**结果**：典型 **U 型曲线**，谷底 **3e-3**（1.296）。左侧欠拟合（1e-4 步长
太小），右侧在噪声中震荡、收敛质量下降（3e-2 达 1.74 但仍收敛不发散）。
最终 baseline 用 3e-3 训出 **1.2994**（24 分钟，1456s）。

---

## 5. 问题四（意外发现）：为什么学习率拉到 3e-2 甚至 1e-1 都不发散？

**问题**：扫到 3e-2 仍未发散，与"调大 lr 就发散"的朴素预期矛盾。想要一个
发散 run 来刻画稳定性边界，却"追不上"发散。

**解决思路**：把它当成机理问题而非运气——逐层剥离稳定机制做对照实验。

**做了什么**（EXP-004 发散探索）：

| 配置 | 结果 |
| --- | --- |
| 有梯度裁剪，lr=3e-2 | 收敛（1.74） |
| 有梯度裁剪，lr=1e-1 | 不发散（8000+ 步 loss 稳在 2.48） |
| 关梯度裁剪，lr=1e-2 | 不发散，但 val 变差到 2.0（有裁剪时 1.41） |
| **关梯度裁剪，lr=1.0** | **step 174 发散**（loss 从 ~5.5 爆炸到 25.98，触发发散保护退出） |

**结论——稳定性双防线**：
1. **梯度裁剪（max_norm=1.0）**：无论 lr 多大，单步更新被强行限幅 → 有裁剪
   时 lr 加到 1e-1 都不炸；
2. **AdamW 自适应**：更新量 ≈ lr × m̂/(√v̂+ε) ≈ lr × O(1)，对梯度尺度归一
   → 关掉裁剪后 lr=1e-2 仍稳（只是效果变差）。

必须**同时突破两道防线**（关裁剪 + lr=1.0）才发散。"单调加大 lr 不足以发散"
是一个反直觉但完全可复现的工程发现，也是本项目最有讲头的结论之一。
（复现：`uv run train_experiment.py baseline --lr 1.0 --max_grad_norm 1e9`）

## 6. 问题五：batch size 怎么选？是不是越大越好？

**问题**：直觉上大 batch 更稳更快，但固定总 token 预算时大 batch 意味着更少
的参数更新次数——需要实验裁决，同时摸清 24GB 显存的上限。

**解决思路**：固定 lr=3e-4 与总 token 预算，扫描 bs 1~224（bs=1 步数过多，
改用 1/16 预算只看趋势）。

**做了什么**（EXP-005）：

| bs | 1 | **16** | 64 | 128 | 160 | 192 | 224 |
| -- | - | ----- | -- | --- | --- | --- | --- |
| 最佳 val | 1.7406 | **1.3218** | 1.3424 | 1.3735 | 1.3910 | 1.4035 | **OOM** |
| 步数 | 78,125 | 80,000 | 20,000 | 10,000 | 8,000 | 6,666 | — |

**结论**：
1. **非单调，存在甜点区（16）**：token 预算固定时小 batch 更新次数多
   （8 万步 vs 1 万步），优化更充分；batch 越大终值越差；
2. **小 batch 有下限**：bs=1 梯度噪声过大，更新次数最多反而最差（1.74）；
3. **显存上限精确定位**：192 稳定训练、224 直接 OOM，4090 (24GB) 上限落在
   192~224 之间；
4. **效果-墙钟权衡**：bs=16 终值最低但步数暴涨（1721s vs bs=128 的 1398s），
   综合**实用折中取 bs=64**。

## 7. 问题六：RoPE / RMSNorm / SwiGLU 这些"标配"，摘掉会怎样？

**问题**：架构组件人人都在用，但"去掉会怎样"没有亲测过；希望用消融给出
组件重要性的第一手排序。

**解决思路**：四组对照消融，全部固定 lr=3e-4（对照基线 1.3470）；SiLU 消融
做**参数量对齐**（SwiGLU d_ff=1344 三矩阵 ≈2.06M vs SiLU d_ff=2048 两矩阵
≈2.10M，公平比较"有无门控"）。

**做了什么与结果**（EXP-007~010）：

| 消融 | 结果 | 结论 |
| --- | --- | --- |
| 去掉 RMSNorm | **step 1842 发散**（train loss 爆到 114） | 归一化对训练稳定性是决定性的 |
| Post-Norm 替代 Pre-Norm | 1.3981 vs 1.3470 | Pre-Norm 更优：残差主干保持恒等映射，梯度更易回传 |
| 去掉位置编码（NoPE） | **1.3447 ≈ 1.3470** | 负结果：因果掩码本身隐式携带位置信息，短序列下显式编码增益有限 |
| SiLU FFN 替代 SwiGLU | 1.3759 vs 1.3470 | 门控有效：逐元素门控带来输入相关的选择性放缩 |

**组件重要性排序**：**RMSNorm（稳定性，最关键） > SwiGLU 门控 ≈ Pre-Norm
（性能） > 位置编码（此任务下影响最小）**。

两个值得强调的点：
- 去掉 RMSNorm 与 lr 无关地发散，和问题五的发散实验互相印证——归一化
  约束激活尺度是深层网络可训的前提；
- NoPE≈RoPE 是**有价值的负结果**：不否定 RoPE（长上下文/外推场景才见分晓），
  而是划清了组件收益的适用边界。

## 8. 问题七：训练出来的模型，生成质量到底如何？

**做法**（EXP-006）：用最佳 checkpoint，temperature=0.8 + top-p=0.9，
prompt "Once upon a time" 自回归生成。

**结果**：语法正确、句子通顺，具备完整"起因—经过—结尾"结构，能正确生成
`<|endoftext|>` 收尾（示例：独立的大熊爬树遇到小鸟、最终交上朋友的故事）。

**定性发现的局限**（定性归因到容量边界）：
1. **重复退化**：同一句话反复出现；
2. **角色/逻辑不一致**：指代混乱、语义奇怪的问句。
这两点是 22.7M 容量 + 有限 token 量的典型边界，靠采样参数只能部分缓解；
"听懂指令、围绕指定主题写"则留给下一阶段 SFT 解决（见
`experiments/SFT工作全记录.md`）。

## 9. 工程细节清单（"做了什么"的完整面）

- **统一实验入口**：`train_experiment.py` 子命令（baseline / lr_sweep /
  batch_sweep / 四类消融 / generate / overfit_test），一条命令复现全部实验；
- **可视化**：`plot_experiments.py` 把 CSV 训练日志自动画成学习曲线
  （按步数/按墙钟、深浅双色、发散标注）→ `figures/`；
- **性能**：`torch.compile` 加速，~23 万 tokens/s（手写算子不拖后腿）；
- **稳健性**：发散保护（loss 爆炸自动退出并保留现场）、mmap 数据读取、
  checkpoint 保存与恢复；
- **测试**：`tests/` 单元测试套件覆盖分词器/模型/优化器/序列化/数据。

## 10. 结论

1. **超参**：最优 lr=3e-3（U 型谷底），baseline val **1.2994**（门槛 1.45）；
   batch 存在甜点区 16（非单调），实用取 64，显存上限 192。
2. **稳定性**：梯度裁剪 + AdamW 自适应两道防线叠加，单调加大 lr 不发散，
   须同时关裁剪且 lr=1.0 才在 step 174 发散——反直觉且可复现。
3. **架构**：RMSNorm 去掉即发散（稳定性关键）；Pre-Norm > Post-Norm；
   SwiGLU 门控 > 无门控 SiLU（参数量对齐下）；NoPE ≈ RoPE（短序列负结果）。
4. **方法论**：冒烟→全量的两级验证、单变量扫描、参数量对齐消融、发散边界
   主动探索——"跑通"之上，实验设计本身是最大的收获。
